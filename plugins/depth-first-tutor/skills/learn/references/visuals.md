# Visuals: when a figure helps

Before every reply, decide in your own reasoning whether a figure would help that explanation. The
decision never appears in the reply: no "a figure would help here", no "I considered drawing this".
The learner sees the figure, when there is one, and the normal explanation.

## When it helps

- spatial or geometric content: a decision boundary, a distance, the shape of a tensor, a
  transformation
- structure: a graph, an architecture, a pipeline, a hierarchy, a data flow
- a side-by-side comparison of two variants whose difference is visible
- anything prose can only describe in more than 3 lines that a figure settles at once

## When it doesn't

A verbal definition, a list of terms, a chronology, a decision table (the table is already the right
form), or a figure that would only decorate and repeat the text next to it.

## How

Use what your environment can show:

1. **A diagram you generate:** SVG or a rendered artifact, where the interface can show it. You
   control the framing, you use the session's own notation, and there are no licensing issues.
2. **ASCII in a code block,** in a plain terminal where images don't render.
3. **An image from the web,** only when the object has to be shown as it is (a UI screenshot, a real
   photo, a specific figure from a paper) and the environment can display or deliver the file. A
   markdown image link doesn't render in a terminal.

## No spoilers

The figure must not give away the answer to the pending verification question. If the only useful
figure would, draw the generic version (without the numbers of the exercise) or wait until the learner
has answered.

The tree render is not a visual in this sense: it always appears, by the rules in `tree.md`.
